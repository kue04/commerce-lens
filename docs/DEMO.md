# 本地后端三分钟演示

本项目是单店铺食品电商的个人作品，数据为合成数据，业务时钟固定 2026-10-22。默认确定性模式没有调用模型。真实 Pi 供应商模式须后续单独验收；以下脚本不能作为真实模型调用演示。

1. 0:00—0:20：说明模式与模拟标识，GET /api/catalog，展示三种支持指标、signals-v1 数据版本与时区。
2. 0:20—1:10：按 BACKEND-QUICKSTART 的命令选择 signals-v1，询问“昨天华东支付金额为什么下降？”。读取 SSE 动作和最终报告，支付金额 100000→70000 元，SKU A -40000、B +10000。
3. 1:10—1:50：打开 E02 的结果表，解释 A 贡献 133.33%、B 贡献 -33.33% 是抵消关系；再看库存证据 A 本期 24/24 小时观测、10 小时零库存，区分可能供应约束与因果结论。
4. 1:50—2:20：在同会话询问“排除 A 呢？”，查看重新查询后的 40000→50000 元，而非复用总额；查询使用服务端授权商品目录展开，不支持无限 SKU 排除。
5. 2:20—2:45：新会话输入“数据异常”，展示 needs_clarification；加载 scenario-S08-v1（需先 db:scenarios）再询问昨天支付金额，展示核心数据缺失阻断，而非误判为销量下降。
6. 2:45—3:00：展示离线评测结果、自动化测试和已知限制。强调没有真实企业上线、没有测得真实模型准确率，也没有证明带来营收提升。

退款演示：“昨天华东退款金额为什么上升？”返回成功退款 300000 分、两个部分退款事件、原因码 unknown 单列。原付款在基期，支付金额历史不被退款回写。件数演示返回 100→70 件，按支付时间，不扣后续退款件数。

## 面试追问

**为什么单 Agent？** 三类问题共享受控数据与证据链。动态选择在工具层，确定性口径和权限在服务端，无需角色传话。

**为什么不让模型写 SQL？** 维度、指标、时间与筛选有有限契约，白名单映射标识符、绑定参数值，才能测试金额口径、查询上限和跨店铺约束。提示词不能代替权限。

**如何保证数字正确？** 金额用安全整数分、支付/退款分开聚合，使用独立 SQL 与人工已知值对照。事实由模板和真实证据引用渲染，校验守恒、比例、版本、scope 和 hash；模型只选择引用。

**最有价值的失败案例？** 数据发布在 10 万订单时因统计信息不足而变慢；ANALYZE 后验证正确性与耗时。另一次 Windows 数据库退出后目录仍被占用，改用 pg_ctl wait 正常关闭；失败结果未伪装通过。

**为什么证据不足也允许 completed？** 核心数据完整时可以完成“变化在哪里”的分析，同时保留 unknown。核心数据不足则 insufficient_data；工具失败而仍有正确比较事实则 partial。不能将库存缺记录解释成零库存。

**取消怎么避免写成功？** 数据库行锁串行化取消和报告/证据保存；终态不可反转。AbortSignal 中断模型和 PostgreSQL，事件持久化后才发送，断线重放不重新执行。

**模型评测是什么结果？** 当前仅有无外部 API 的确定性管线评测与明确 faux transport 的 Pi Core 集成。B 单次模型工具选择和 C 真实 Pi 多轮模型对比尚未运行。数值工具测试不是模型泛化能力证明。
